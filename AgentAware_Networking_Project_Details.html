Agent-Aware Networking

In-Network Classification and Differentiated Transport QoS for AI-Agent Traffic on a Programmable Data Plane

BCSE308L/P Computer Networks · Research Project — Detailed Project Description · August 2026
Goal: working prototype + Mininet/BMv2 evaluation + IEEE-format research paper for publication

1 · Project Overview

One-liner. A network switch (P4/BMv2 or eBPF pipeline) that recognizes AI-agent traffic — MCP tool-calls, A2A flows, agentic browsers — per-packet at line rate and, in the same forwarding pipeline, assigns it a dedicated transport treatment: its own queue, scheduler share, DSCP/ECN marking, and admission control. Bursty, machine-paced agent flows get a controlled lane instead of degrading human interactive traffic.

Outcome. A research paper (IEEE format) presenting the system, a working prototype, and a four-baseline experimental evaluation in Mininet/BMv2 — targeting publication. The paper’s headline result: measurable tail-latency protection for human traffic under agent-traffic bursts (target ≥30% p99 reduction) at negligible data-plane cost (<5% added per-packet latency).

Why now. AI-agent traffic is a 2025–2026 phenomenon with verified data behind it, the research community has only reached the detection stage, and no existing work performs agent classification in the forwarding path or couples it to QoS — a clear, defensible research contribution.

2 · Motivation (verified statistics)

The internet’s traffic mix has structurally changed. All figures verified against primary sources (Aug 2026); phrasing reflects the exact scope of each claim.

  • 53% of internet traffic is automated (Thales 2026 Bad Bot Report, 13th edition, full-year 2025 data): bad bots 40% (up 3 points YoY), benign automation 13%, human traffic down to 47% from 49%.
  • AI agents have emerged as a third traffic category alongside traditional good and bad bots — interacting directly with applications and APIs, running real browsers with valid fingerprints and human-pattern interaction, defeating classic detection.
  • AI-driven bot attacks surged 12.5× in 2025 vs 2024 — daily blocked attacks rose from 2 million to 25 million. (Scope note: 12.5× refers to attack volume specifically, not all agent traffic.)
  • IETF contributors are actively proposing differentiated treatment of AI/agent traffic, including agent policy-aware networks and gateway policies for DSCP, traffic classes, queues, shaping, and policing (draft-zhang-rtgwg-agent-policy-aware-network-01; draft-zhao-opsawg-agent-gateway-policy-00). These are individual Internet-Drafts, work in progress, and not IETF consensus.

The concrete harm: an agent fires 50 parallel MCP tool-calls across the same link as a human video call. Every switch on the path sees 51 indistinguishable TLS flows on port 443 and queues them together; the human’s packets wait behind the machine-paced burst, and that queuing delay is the p99 latency spike. The network cannot fix what it cannot distinguish.

3 · Problem Statement

Existing QoS machinery (DiffServ, port/application-based classification, endpoint-set DSCP) cannot recognize AI-agent traffic: agents use real browsers, valid TLS fingerprints, and standard ports. Existing agent-detection solutions (Cloudflare signed agents / Web Bot Auth, DataDome Agent Trust, Akamai) operate only at the HTTP/CDN edge — they terminate TLS, see only traffic routed through them, react on request timescales, and offer only allow / block / rate-limit / monetize actions. No mechanism exists inside the network forwarding path that identifies agent traffic per-packet at line rate and gives it differentiated transport service.

4 · Core Concepts

4.1 · Forwarding plane vs control plane vs application edge

Every switch/router splits into a control plane (the software brain: routing protocols, controller interaction, table updates; millisecond–second timescales) and a forwarding plane (data plane — the pipeline every packet physically traverses: parse headers → match tables → apply actions → queue to output port; nanosecond–microsecond timescales). The application edge (WAF/CDN/proxy) is a different location entirely: it terminates TLS and inspects HTTP requests after the fact. In this project the classification decision is made in the forwarding plane — per packet, at line rate, inside the device, for any traffic crossing it. P4 is to switches what code is to CPUs: we are not building a switch; we are writing the program a programmable switch runs. BMv2 is the software emulator of such a switch used for development and evaluation.

4.2 · Transport QoS as the action space

Once a flow is labeled, the action is a service treatment, not an access decision: DSCP/traffic-class rewrite; assignment to a per-class queue with a bounded scheduler weight; a class-specific ECN marking profile (shaping how senders’ congestion control backs off); and admission control / rate shaping of new agent flows under congestion — including a human-traffic-protection mode that caps the aggregate agent share of a congested link. Agent traffic is never rejected; it is isolated into an engineered lane. Misclassification therefore degrades service class rather than blocking anyone — a graceful failure mode no allow/block system offers.

4.3 · The coupling is the contribution

Neither half is new alone: agent fingerprinting exists (application layer), in-network ML on P4 exists (Mousika, IIsy), and QoS queues are decades old. What does not exist anywhere is the coupling: the switch itself recognizes “this is an AI-agent flow” and, in the same pipeline pass, changes how that packet is serviced. The deployment property that follows is single-box incremental deployability: no internet-wide adoption, no new protocol, no third-party cooperation — one device at a choke point (campus/enterprise gateway, datacenter leaf, the switch fronting an API/LLM-serving cluster) benefits its domain immediately. One honest scope note for the paper: DSCP markings are routinely bleached at AS boundaries, so the QoS treatment is meaningful within the deploying domain — which is where the queues and the congestion live anyway.

5 · Literature Review and Research Gap

The relevant literature falls into three streams: (A) identifying agent/bot traffic, (B) running ML classification inside programmable data planes, and (C) networking research around agent protocols. Each stream supplies a building block; none performs agent classification in the forwarding path, and none couples agent identity to a QoS action. 5.4 · Gap synthesis

Stream A detects agents but cannot act, operates at the application layer, and its best results lean on signals a switch never sees — while its own ablations show the network layer alone is unsolved. Stream B acts inside the data plane at line rate but has never targeted agent traffic; its closest action-coupling precedent (ACC-Turbo) keys on attack aggregates, not traffic identity. Stream C and emerging July 2026 Internet-Drafts propose network-aware agents, explicit policy intents, and gateway-recognized agent QoS, but do not demonstrate behavioral inference from bounded forwarding-path features. Gap statement (for the paper): the verified sources do not present an evaluated system that infers agent classes from forwarding-path behavior without cooperative endpoint or gateway identity and immediately couples that inference to in-network QoS treatment.

6 · Novelty — Four Distinguishing Axes

  1. Location — forwarding plane, not application edge. Acts inside the switch, per packet, at line rate, on any traffic crossing the device; no proxying, no TLS termination, works beyond HTTP.
  2. Action — transport QoS, not access control. Queueing, scheduling, ECN/congestion signaling, admission control; an engineered lane, not a verdict.
  3. Trigger — agent/MCP identity specifically, not generic application classes (classic QoS literature) and not GPU-cluster AI-workload prioritization (AI-fabric work).
  4. Features — agent-protocol and behavioral fingerprints keyed directly to the QoS action in the same pipeline. The contribution is this coupling.

Framed as paper contributions: (C1) the first characterization of agent traffic as a distinct in-network traffic class with line-rate-computable features; (C2) a data-plane classifier + QoS coupling architecture with a controller-assisted reclassification loop; (C3) a reproducible evaluation showing human-traffic tail-latency protection under agent bursts against four baselines; (C4) an adversarial analysis showing timing-based evasion is self-penalizing.

7 · Classification Parameters: Agent vs Human

Five feature families, ranked by expected discriminative weight. Families 1–3 carry the classifier; family 4 saturates against browser-driven agents; family 5 is deployment-dependent.

  1. Inter-packet timing statistics (strongest signal). Human flows contain think time: heavy-tailed gaps of hundreds of milliseconds to seconds, high variance. Agent flows are machine-paced: near-deterministic inter-arrival times (IATs), sub-ms to tens-of-ms gaps, low coefficient of variation. Computed per-flow in P4 registers: EWMA IAT mean/variance, min/max IAT, coarse timing entropy. Key property: evasion is self-defeating — an agent inserting human-like think time becomes as slow as a human, forfeiting its own purpose.
  2. Burst and fan-out structure. Agents fire parallel tool-calls: N simultaneous connections from one source with synchronized starts; humans open connections gradually. Features: new-flow arrival rate per source (count-min sketch), concurrent flows per source, burst length in packets, destination diversity per time window. This family directly predicts the congestion harm being solved.
  3. Packet-size and flow-shape statistics (survive encryption). Sizes of the first N packets of a flow (highly discriminative in encrypted-traffic ML), packet-length distribution moments/histogram bins, upstream/downstream byte ratio (agents: large structured JSON-RPC requests up, SSE streams down; human browsing: heavily download-asymmetric), flow duration. MCP-over-SSE signature: a long-lived flow carrying near-periodic small event/keepalive packets.
  4. TLS handshake metadata (JA4 family — useful, never the anchor). The ClientHello is plaintext even in TLS 1.3: cipher-suite and extension counts/order, ALPN, GREASE, post-quantum key-exchange presence, SNI. Python/Go/Node agent stacks differ visibly from browsers — but agents driving real Chromium present browser-identical fingerprints (network-layer-only attribution: ~45–60%), and Encrypted ClientHello will erode SNI visibility over time. Treated as one input to the tree, with these limitations stated in the paper.
  5. Explicit/cooperative signals (deployment-dependent). Web Bot Auth signature headers (RFC 9421) and MCP/A2A JSON-RPC protocol signatures travel inside TLS payloads — invisible mid-path, visible behind a TLS-terminating load balancer or on plaintext east–west datacenter traffic. Framing: the classifier runs on families 1–4 everywhere and gains family 5 as bonus features in TLS-terminated deployments.

8 · Implementation in Detail

8.1 · Data plane (P4 on BMv2, in Mininet)

The P4 program defines the full packet path. Parser: Ethernet → IPv4 → TCP/UDP; on a flow’s first packet, parse TLS ClientHello fields (cipher/extension counts, ALPN, SNI length bucket). Feature stage: hash the 5-tuple to a flow index; update per-flow register arrays — last-seen timestamp, EWMA IAT mean and variance, packet count, directional byte counters, first-N packet-size slots; update per-source count-min sketch for new-flow rate and fan-out. Classification stage: the offline-trained decision tree is compiled into match-action tables using range matches over the register values (the Mousika/IIsy distillation recipe), emitting a 2-bit class label in packet metadata. Action stage: the label drives DSCP rewrite, egress-queue selection (three class queues with weighted round-robin), a per-class ECN marking threshold, and a per-class meter for admission control of new flows. Human-protection mode: when the egress queue depth crosses a congestion threshold, scheduler weights shift to a protective preset that caps the aggregate agent share.

8.2 · Control plane (SDN slow path)

A Ryu (or ONOS) controller performs what cannot or should not run per-packet: it installs and updates the class→queue/weight policy; receives first-packet punts to compute the full JA4 string and, where visible, verify Web Bot Auth signatures; and runs the entropy-shift reclassification loop — periodically reading flow statistics and reassigning the class of flows whose timing behavior has drifted (an agent mimicking human pacing, or a misclassified human flow). The per-packet decision always stays in the device; the controller only refines it.

8.3 · ML workflow

Python + scikit-learn: train a shallow decision tree (depth ≤ 8) on the labeled traffic corpus (§9.1); export split thresholds; compile mechanically into P4 table entries. Feature importances are reported in the paper — timing and burst features are expected to dominate, reinforcing the design argument that line-rate-visible behavior suffices for class-level (not framework-level) discrimination.

8.4 · Traffic harness

Ground truth comes from real systems, not synthetic labels: an instrumented target (small web app + a real MCP server) receives traffic from actual agent frameworks (e.g., Browser Use, Claude with MCP tools, AutoGen, a Playwright-driven agentic browser) run in containers, with pcaps captured at the target — mirroring the methodology of the fingerprinting literature. AgentReady’s WebMCP tool-call traffic serves as an additional realistic MCP workload source. Human traffic: replayed public anonymized traces (MAWI backbone captures; CAIDA passive traces) plus captured interactive browsing sessions for labeled human flows. Background load: iperf3 bulk flows.

9 · Evaluation Plan

9.1 · Setup

Mininet topology with the BMv2 switch at a choke point; link capacities scaled down (10–50 Mbps) so relative congestion behavior is preserved despite BMv2’s software forwarding limits — standard, defensible practice in P4 evaluations, stated explicitly in the paper. Traffic mixes sweep agent share from 10% to 90% and burst intensity across a grid; each configuration runs with multiple seeds and reports confidence intervals.

9.2 · Baselines (four)

  • FIFO / best-effort (no differentiation);
  • Standard DiffServ with port/application-based marking;
  • Per-flow fair queuing;
  • An application-layer rate limiter (edge/WAF-style) — demonstrating that the in-network approach reacts faster and covers non-HTTP paths.

9.3 · Metrics and targets

  • Human/interactive flow p50/p95/p99 latency under agent burst — target: ≥30% p99 reduction vs best baseline;
  • Agent tool-call completion time (interactive-agent class must not be starved);
  • Classification precision/recall per class at line rate;
  • Data-plane overhead: added per-packet latency (target <5%), table entries, register memory footprint;
  • State scaling: accuracy and memory vs concurrent flow count (1k → 100k, with sketch-based approximations beyond exact-state capacity);
  • Adversarial evasion: agents deliberately mimicking human pacing — report both the accuracy drop and the agent’s throughput self-penalty, converting the “evasion is self-defeating” argument from claim to measurement.

The paper’s centerpiece figure: human p99 latency held flat during an agent storm with the system on, versus the spike under every baseline.

  • Get the centerpiece demo working: agent burst hits the link, human p99 stays flat

Phase 4 — Evaluation (weeks 11–13)
